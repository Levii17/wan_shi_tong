01
Centralized vs distributed VCS

Before modern tools like Git, teams used Centralized Version Control Systems (CVCS). The world has since shifted almost entirely to Distributed systems (DVCS) — understanding why explains Git's core design.

Centralized (old way)

e.g. SVN, Perforce

One single master copy of the code history lives on a central server. Every developer must connect to it to commit, view history, or collaborate.

Single point of failure — if the server goes down, no one can save work or access history
Requires a network connection for almost every operation
Distributed (Git way)

Git, Mercurial

Every developer who clones the project gets a 100% complete copy of the entire project history on their local machine.

No internet needed to commit, view history, or revert
Server failure is recoverable — any developer's copy can restore everything
Key insight

In a distributed system, there's no "master" — just many equal copies. The server on GitHub is just another copy that the team has agreed to treat as the official source of truth.

02
The three states of Git

The biggest hurdle for Git beginners: code doesn't jump straight into history when you save a file. Git tracks files across three distinct local zones before they ever touch the internet.

Working directory
Modified
Your actual folder. You're actively editing. Git sees the changes but hasn't tracked them.
git add
Staging area
Staged
A sandbox where you curate the next snapshot. You choose exactly which changes to include.
git commit
Local repository
Committed
Permanently saved as a cryptographic snapshot in your .git directory.
Photography studio analogy

Working directory — people are walking around, changing clothes, getting into position.
Staging area — you say "everyone freeze, smile!" You've framed the perfect shot.
Local repository — you click the shutter. The photo is saved permanently to the memory card.

The essential three commands
# 1. Start tracking a project folder\ngit init\n\n# 2. Move files from Working Directory → Staging Area\ngit add index.html\n\n# 3. Take the snapshot, save it to Local Repository\ngit commit -m "Fix the login page layout bug"
03
Branching and merging

In the old days, two developers editing the same file at the same time would overwrite each other's work. Git solves this with branching — letting each developer work in an isolated parallel universe.

Branch
A lightweight pointer to a specific commit. Lets you diverge from main to build a feature or fix a bug in isolation.
Merge
Once a feature is complete, the isolated branch is merged back into main, combining both histories.
Merge conflict
If two developers changed the exact same line of the same file on different branches, Git halts and forces a human to resolve.
What a merge conflict looks like in your file
<<<<<<< HEAD
console.log("Hello from Main Branch!");
=======
console.log("Hello from my Feature Branch!");
>>>>>>> feature-branch

You must delete the markers, choose (or combine) the two versions, save the file, and make a fresh commit to complete the merge.

04
Git vs GitHub — not the same thing

A classic exam mistake: treating Git and GitHub as interchangeable. They are entirely distinct tools that happen to work together.

Git

The local tool

Open-source software that runs in your computer's terminal. Tracks files, manages history, handles branches. Works completely offline — no internet or account required.

Runs on: your machine
GitHub

The cloud platform

A website (owned by Microsoft) that hosts Git repositories in the cloud. Adds collaboration tools: pull requests, code review, issue tracking, CI/CD.

Runs on: github.com servers
The relationship

You use Git to manage your code locally. You use GitHub to share that code with the world. Git would work fine without GitHub. GitHub would be useless without Git.

05
Git's data model — snapshots, not deltas

Git's speed and flexibility come from one fundamental design decision: it stores data as snapshots, not differences.

Delta-based (SVN)

Storing differences

Stores the original file, then a list of additions and deletions for each version. To see version 5, the system must stitch together the original plus all 5 sets of changes dynamically — slow for large histories.

Snapshot-based (Git)

Storing full states

Every commit takes a picture of all files at that exact moment. If a file hasn't changed, Git doesn't duplicate it — it stores a lightweight link to the identical previous version.

Analogy

Delta-based systems are like keeping a running list of edits on a Google Doc. Git is like taking a full photograph of your entire project folder every time you hit save — but a smart camera that reuses identical parts automatically.

Branches are just pointers — that's why they're instant

In older systems, creating a branch meant copying the entire project folder. In Git, a branch is a 41-byte text file containing one SHA-1 hash. Creating a branch is instantaneous regardless of project size.

06
SHA-1 hashes — cryptographic integrity

In Git, it is physically impossible to secretly alter a file or silently lose data. Every piece of content is identified by a cryptographic fingerprint called a SHA-1 hash.

1
Git hashes everything on commit
When you commit, Git runs all file contents, folder structure, author, and timestamp through SHA-1.
2
The output is a unique 40-character string
24b9da6552252987aa493b52f8696cd6d3b00373
3
Any change — even one character — produces a completely different hash
Git doesn't identify files by name; it identifies them by hash.
Why this matters

You can't rewrite history secretly. The entire project history is cryptographically tamper-evident — every commit knows the hash of its parent, forming an unbreakable chain.

07
Merge strategies — how Git stitches histories together

When you run git merge, Git picks one of two strategies depending on how the two branches evolved relative to each other.

Fast-forward merge

The straight line

Occurs when main has had zero new commits since you branched off. Git simply slides the pointer forward. No new commit.

Clean, linear history
No extra merge commit
3-way merge

The diverged path

Occurs when main received new commits while you were on your branch. Git compares three snapshots into a new Merge Commit.

Preserves full history of both branches
Creates an extra merge commit; history is non-linear
Analogy — fast-forward

You and a friend are reading the same book. You paused at Chapter 5; your friend kept reading to Chapter 10. To catch up, you don't need to combine notes — you just flip your pages forward.

08
Remote repositories — sharing code over the internet

When you push your local branches to GitHub, you're synchronizing two independent database instances. Here's how Git manages that connection.

origin
Default nickname Git gives to your main cloud repository. Alias for a URL like https://github.com/user/repo.git.
Remote tracking branches
Read-only local mirrors of what the cloud looks like: origin/main, origin/feature-x.

The 4 essential network commands

Pull requests and code review

1
Open the PR
Formal message to your team: "Please review my feature." GitHub shows a visual diff.
2
Code review
Teammates comment, request changes. The author pushes fixes; the PR updates live.
3
Automated testing (CI/CD)
Cloud servers run automated tests to verify nothing is broken before merging.
4
Merge
After approval, someone clicks "Merge." GitHub handles the 3-way merge in the cloud.
09
GitHub features — beyond a code storage folder

GitHub adds collaboration, automation, and project management on top of Git.

git clone

Local copy

Downloads the repo to your machine. If you don't have write permission, you can't push changes back.

Fork on GitHub

Cloud copy under your name

Creates a copy of someone else's repo inside your own GitHub account. You have full write access to your fork. Then open a PR back to the original project.

Analogy

Cloning = buying a cookbook; forking = photocopying the book under your own name, improving a recipe, and sending a letter to the chef.

The fork workflow

Fork the original repo → Clone your fork → Make changes → Push to your fork → Open a Pull Request from your fork to the original project.

GitHub Actions — the automation engine (CI/CD)

Linting
Check code for syntax errors and style violations on every PR.
Security tests
Run thousands of tests to ensure no secrets are accidentally committed.
Auto-deploy
Push approved code to your host (AWS, Vercel) the moment a PR is merged.
Feature What it does
Issues Built-in ticket system for bugs, features, questions.
Projects Kanban board with columns like "To Do", "In Progress".
Contribution graph Green-square grid on every profile showing activity.
Stars & forks Community approval metric for repositories.
10
Branching strategies — team rules for using Git

When multiple developers push to the same repo, chaos ensues without agreed rules. The two dominant strategies reflect very different philosophies about speed vs safety.

GitFlow

The traditionalist

Rigid, structured model with multiple long-lived branches (main, develop, feature/*, release/*, hotfix/*).

Extremely safe — code passes multiple review layers
Slow and complex — features sit isolated for weeks
Trunk-based development

The modern speedster

Industry standard at Netflix, Facebook, Google. Everyone works from a single central branch. Tiny short-lived branches merge back within hours.

Fast, low conflict risk — small changes mean small merges
Requires strong automated test coverage
Metric GitFlow Trunk-based
Branch lifespan Weeks or months Hours or days
Merge frequency Infrequent, large batches Multiple times per day
Used by Enterprise software, game studios Netflix, Google, Facebook
Feature flags — trunk-based's secret weapon

A conditional toggle in code. The unfinished feature is deployed to the live server, but a flag hides it from users. When flipped ON, the feature appears instantly — no new deployment needed.
